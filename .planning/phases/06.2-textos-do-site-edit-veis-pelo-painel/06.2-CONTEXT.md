# Phase 06.2: Textos do site editáveis pelo painel - Context

**Gathered:** 2026-10-26 (pedido do cliente na thread "Editar todos os textos pelo painel")
**Status:** Ready for execution

<domain>
## Phase Boundary

Pedido do cliente (2026-10-26): "todos os textos de todas as páginas devem ser possíveis de ser trocados
pelo painel administrador". Hoje só são editáveis pelo painel: as 6 páginas institucionais (coleção
`pages`), Contato e endereço (global `contact`), festas, planos, modelos, contos, dicas e anúncios.
Todo o resto (títulos, chamadas, botões, rótulos, estados vazios, menu, rodapé, confirmação 18+,
títulos e descrições do Google) está escrito no código.

Requisito novo: **PAINEL-10** — a equipe troca pelo painel qualquer texto fixo das páginas do site
(área aberta e área do assinante), sem ajuda técnica; apagar um campo volta ao texto original.

**Dentro do escopo:** todo texto visível escrito em `src/app/(frontend)/**` e `src/components/**`
(menos `components/admin`), `src/lib/site/nav.ts` (rótulos do menu), `src/lib/age-gate/self-declaration.tsx`
(confirmação 18+), metadados de página (`title`/`description` de `metadata`/`generateMetadata`).

**Fora do escopo (dizer ao cliente):**
- Mensagens de erro e de validação de formulário (`src/lib/errors/**`, `src/lib/*/actions.ts`,
  `*-rules.ts`, `?erro=codigo` → mensagem). São mensagens do sistema; ficam no código (quick
  2026-10-24-mensagens-de-erro já as padronizou). `src/app/global-error.tsx` também (fora do layout).
- E-mails automáticos (`src/lib/email/**`).
- O próprio painel (`/admin`, `src/components/admin/**`, rótulos de coleções).
- Textos só para leitor de tela (`sr-only`, `aria-label`) e `alt` gerado por código: ficam no código.
- Conteúdo que já é editável (páginas, contato, festas, planos etc.) continua onde está.
</domain>

<decisions>
## Implementation Decisions

- **T-01 Um global por área, grupo "Textos do site".** Cada área do site vira um global Payload
  (`textos-geral`, `textos-inicio`, …) no grupo de menu **"Textos do site"**. Forms menores e mais
  fáceis de achar do que um global gigante com abas. Campos agrupados em `collapsible` por seção da
  página (sem efeito no banco).
- **T-02 Registro único em código.** Cada área é um arquivo `src/lib/textos/areas/<area>.ts` com
  `{ slug, rotulo, descricao, campos: { nomeDoCampo: { rotulo, padrao, secao?, longo?, ajuda? } } }`.
  O global, o tipo TypeScript e o texto padrão saem do mesmo registro. `padrao` = texto atual do site,
  **copiado letra por letra** (acentos, travessões, pontuação), para nada mudar visualmente e os e2e
  existentes continuarem passando.
- **T-03 Vazio = texto original.** Campos não são obrigatórios; `defaultValue = padrao` (o painel já
  abre preenchido). Na leitura, valor vazio/só espaços → `padrao`. Assim a equipe nunca "some" com um
  texto e sempre consegue voltar ao original apagando o campo.
- **T-04 Leitura no servidor.** `getTextos(area)` (server-only, `cached` com tag `textos:<area>`) →
  objeto tipado com todos os campos já mesclados. Nunca lança: erro de banco (ex.: prerender sem banco)
  → registra e devolve os padrões. Componentes de servidor chamam `getTextos` direto (sem mudar a
  assinatura de componentes compartilhados). Componentes cliente recebem os textos por prop do pai
  servidor (`textos={t}` ou campos soltos).
- **T-05 Contexto só para a área "geral".** `TextosGeraisProvider` (client) no layout do site expõe
  os textos da área `geral` (menu, rodapé, galeria/lightbox, paginação, página de erro) para
  componentes cliente compartilhados (`Lightbox`, `Gallery`, `Nav`, `MobileMenu`, `error.tsx`) sem
  mudar quem os chama. As outras áreas NÃO vão para o contexto (peso de página, MIDIA-03).
- **T-06 Variáveis entre chaves.** Partes dinâmicas usam `{nome}` no texto e `preencher(texto, { nome })`.
  A `ajuda` do campo lista as variáveis ("Use {plano} para o nome do plano."). Variável que a equipe
  apagar simplesmente não aparece; chave desconhecida fica como está.
- **T-07 Texto com link ou negrito no meio** é dividido em campos (antes / texto do link / depois).
  Plurais e contagens feitos por código (ex.: "1 foto"/"3 fotos") podem virar dois campos
  (singular/plural com `{n}`) ou ficar no código quando separar confundir a equipe.
- **T-08 Acesso.** `read: () => true` (são textos públicos do site; nada sensível), `update: isStaff`.
  `afterChange` expira `textos:<area>`. Sem rascunho/versões (salvar publica; apagar volta ao original).
- **T-09 Metadados.** `export const metadata` vira `generateMetadata` lendo `getTextos` onde houver
  título/descrição fixos; `buildPageMetadata` continua sendo usado. O sufixo " · Paraíso Brasília" e
  rótulos técnicos (`rating`, RTA) ficam no código.
- **T-10 Uma migração no fim.** Todos os globals entram numa única migração gerada depois que todas
  as áreas estiverem preenchidas (plano 06). Antes disso a verificação é typecheck, lint e testes unitários.
- **T-11 Nomes.** Nomes de campo em camelCase ASCII, ≤ 40 caracteres, sem `id`, `globalType`,
  `createdAt`, `updatedAt`, `_status`. Slug do global `textos-<area-kebab>` (tabela ≤ 63 caracteres).

### Claude's Discretion
- Divisão exata dos campos e das seções de cada área, desde que cubra todo texto visível da área.
- Rótulos e ajudas em português simples para equipe não técnica ("Título do topo", "Botão verde").
</decisions>
