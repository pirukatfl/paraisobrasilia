## Summary

Payload 3.91 supports several auth collections in one config. A second auth collection **`assinantes`** (slug requested by the orchestrator) gets its own login, password hashing (PBKDF2, `salt`/`hash`), lockout (`maxLoginAttempts`/`lockTime`), DB-backed sessions (`useSessions: true` is the default in 3.91: each login stores a session id in the user doc and the JWT carries `sid`, so logout and password changes revoke sessions) and a configurable `tokenExpiration`. The JWT strategy reads the `collection` claim and loads the user from that collection on every request with `overrideAccess: true`, so `req.user.collection` tells staff (`users`) from subscribers (`assinantes`). The admin panel already refuses non-`users` principals (`getAccessResults`: `canAccessAdmin` is false unless `user.collection === config.admin.user`).

Three properties of Payload found in the source change the plan:

1. **Every existing access function treats any logged-in principal as staff** (`const isStaff = ({ req }) => Boolean(req.user)` in Parties, Pages, SpaceItems, Models, Media, Videos, Contact, `imageAuthorization`, and `Users` itself; `read: req.user ? true : published`). The moment a subscriber can log in, they could create/edit parties, read drafts and list staff accounts through `/api/*`. This must be fixed **before** the `assinantes` collection ships (first task of the phase), with a regression test.
2. **`POST /api/{auth-collection}/first-register` creates a user with `overrideAccess: true` whenever the collection is empty** (`registerFirstUserOperation`). Production will start with zero subscribers until Phase 6, so anyone could create the first subscriber account with arbitrary data. A `beforeOperation` guard on `assinantes` must reject `create` unless the caller is staff or the call carries a trusted `req.context` flag (migrations/tests).
3. **There is one auth cookie for all collections**: `${cookiePrefix}-token` (`payload-token`). A browser holds one identity at a time; logging in as a subscriber replaces a staff admin session and vice versa. Acceptable (document for staff: test subscriber logins in a private window); e2e tests use separate browser contexts.

Also relevant: with no e-mail adapter Payload uses `consoleEmailAdapter` (logs "Email attempted without being configured" with recipient and subject, not the token). The public `POST /api/assinantes/forgot-password` would still create tokens (and overwrite a staff-generated link). It is blocked with the same `beforeOperation` guard (operation `forgotPassword`) unless the staff service passes a context flag; `disableEmail: true` is used by the service.

Entitlement is **computed, never flagged** (ARCHITECTURE Anti-Pattern 3): a `subscriptions` collection stores periods (start, end, status, payment record); access = a non-ended period with `startsAt <= now < endsAt`, evaluated on the server per request. `endsAt` is the São Paulo midnight after the last valid day, so a subscription "válida até 17/11/2026" stops at 18/11/2026 00:00 BRT without any job. A denormalised `accessUntil` on the subscriber (recomputed by subscription hooks) powers the admin list column and the "vencem em 7 dias" panel.

**Primary recommendation:** seven sequential vertical slices (every slice but the last two changes the Payload schema, and migration snapshots serialize): (1) role-safe access + `assinantes` login with persistent session and a members area shell; (2) `plans` + "Assine Já"; (3) periods + entitlement + "Minha assinatura" + restricted placeholder; (4) audit log + liberar/renovar/encerrar in the panel; (5) passwords (self change, staff temporary password, staff reset link); (6) "vencem em 7 dias" + phase-wide leak sweep; (7) docs, deploy and client check.

### Pattern 1: `assinantes` auth collection (ASS-01, D-01)
```ts
auth: {
  tokenExpiration: 60 * 60 * 24 * 30,      // 30 days: JWT exp, session expiry and cookie Expires
  maxLoginAttempts: 5, lockTime: 600_000,  // same as staff
  useSessions: true,                        // default; explicit for readers
  cookies: { sameSite: 'Lax', secure: serverURL.startsWith('https://') },
  forgotPassword: { expiration: 48 * 3600 * 1000 },  // staff-generated link (D-04)
}
```
Fields: `name` (text required, "Nome ou apelido"), `whatsapp` (text, digits `^55\d{10,11}$`, optional, staff contact), `staffNotes` (textarea, field access read/update staff only), `mustChangePassword` (checkbox, read-only in admin, sidebar). Later slices add `accessUntil` (date, read-only), joins `periodos` (subscriptions.assinante) and `historico` (audit-log.assinante).
Access: `read` staff → true, subscriber → `{ id: { equals: req.user.id } }`, else false; `create/update/delete/unlock` staff only; `admin: () => false`. Guard `beforeOperation`: operation `create` without staff user and without `req.context.trustedCreate` → `Forbidden` (closes `first-register`); operation `forgotPassword` without `req.context.staffPasswordLink` → `Forbidden`.
Admin: group "Assinantes", `useAsTitle: 'name'`, defaultColumns `['name','email','accessUntil','updatedAt']`, `listSearchableFields: ['name','email','whatsapp']`, description "Crie a conta depois de conferir o comprovante. A conta pode existir sem acesso: libere em 'Assinatura'."

Creating an account requires a password (Payload auth). Staff type a temporary password in the native create form; a hook marks `mustChangePassword: true` whenever staff set a password (D-04).

### Pattern 2: Role-safe access helpers (security prerequisite)
```ts
export const isStaff = ({ req }: { req: { user?: { collection?: string } | null } }) => req.user?.collection === 'users'
export const isAssinante = ({ req }) => req.user?.collection === 'assinantes'
export const staffOrPublished = ({ req }) => (isStaff({ req }) ? true : { _status: { equals: 'published' } })
```
Replace every local `isStaff`/`Boolean(req.user)`/`req.user ? true : …` in Parties, Pages, SpaceItems, Models, Media, Videos, Users, Contact and `imageAuthorization`. `Users` also gets `unlock: isStaff` (Payload's default unlock access is "any logged-in user"). Regression int test: a subscriber principal (Local API `user: { ...doc, collection: 'assinantes' }`, `overrideAccess: false`) cannot create parties, read drafts, read `users`, update `contact`, read `imageAuthorization`, create `assinantes`.
Optional hardening in the same task: Payload `csrf: [NEXT_PUBLIC_SERVER_URL]` so a cookie sent with a foreign `Origin` is ignored (`extractJWT` cookie method). Same-origin admin and server actions keep working; e2e REST helpers use the `Authorization: JWT` header and are unaffected.

### Pattern 3: Login, logout and the members route group (ASS-01)
- `/entrar` (public, noindex, dynamic): a plain `<form action={entrar}>` (server action, works without JS). `entrar(formData)`: trim/lower-case e-mail, require password; `payload.login({ collection: 'assinantes', data })`; set cookie with `generatePayloadCookie({ collectionAuthConfig, cookiePrefix: payload.config.cookiePrefix, returnCookieAsObject: true, token })` → `(await cookies()).set(name, value, { httpOnly: true, sameSite: 'lax', secure, expires, path: '/' })`; `redirect(safeNext(next))`. Errors: `AuthenticationError` → `/entrar?erro=credenciais` ("E-mail ou senha incorretos."); `LockedAuth` → `?erro=bloqueado` ("Muitas tentativas. Aguarde 10 minutos ou fale com a equipe pelo WhatsApp."). Never reveal whether the e-mail exists.
- `safeNext(next)`: only paths starting with `/area-do-assinante` (no `//`, no scheme, no backslash); default `/area-do-assinante` (open-redirect guard, unit-tested).
- `sair()`: `logout({ config })` from `@payloadcms/next/auth` (revokes the session, deletes the cookie) → `redirect('/')`.
- Route group `src/app/(frontend)/(membros)/` with a `layout.tsx` that renders only chrome (sub-nav "Minha assinatura · Conteúdo exclusivo · Trocar senha · Sair") and `export const dynamic = 'force-dynamic'`. **Authorization lives in the DAL** (`session.ts`): `getAssinante = cache(async () => { const { user } = await payload.auth({ headers: await headers() }); return user?.collection === 'assinantes' ? user : null })`; `requireAssinante(path)` redirects to `/entrar?next=path`; every page and every server action calls it (Next docs: layouts do not re-render on navigation and do not gate child segments or actions). Staff principals are not subscribers → redirected to `/entrar`.
- Proxy (Next 16 `proxy.ts`) is **not** needed: there are no static members routes; skip it to avoid a second source of truth.

### Pattern 4: Members pages never cached or indexed
- Pages read `headers()`/cookies → dynamic rendering; Next sets `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` (docs `self-hosting.md`). Never wrap subscriber-specific reads in `cached()`/`unstable_cache`.
- `next.config.ts` `headers()`: `X-Robots-Tag: noindex, nofollow` for `/area-do-assinante/:path*`, `/entrar`, `/nova-senha` also in production (the global rule only applies outside production).
- `robots.ts` production disallow gains `/area-do-assinante`, `/entrar`, `/nova-senha`; the sitemap never lists them (only `/assine-ja`).
- Metadata `robots: { index: false, follow: false }` on those pages.
- e2e asserts the headers on `/area-do-assinante` (logged in) and `/entrar`.

### Pattern 5: Periods and entitlement (ASS-03, ASS-04, D-05)
`subscriptions` (labels "Período de assinatura"/"Assinaturas e pagamentos", group "Assinantes"): `assinante` (rel, required, index), `plan` (rel `plans`, optional — empty = cortesia/ajuste), `startsAt` (date, required), `endsAt` (date, required; computed from plan in `beforeValidate` when empty), `status` (select `ativa` | `encerrada`, default `ativa`), `closedAt` (date, read-only), `payment` group {`amount` number ≥ 0, `method` select pix | pagbank | dinheiro | transferencia | cortesia | outro (required), `paidAt` date, `note` textarea}, `summary` (text, read-only, `useAsTitle`, e.g. "Mensal · 19/10/2026 a 17/11/2026"). Access: read/create/update staff; **delete false** (history is kept; "Encerrar" instead). No drafts.

Pure rules (`periods.ts`, unit-tested first):
- `spDate(instant) → 'YYYY-MM-DD'` in America/Sao_Paulo; `spMidnight('YYYY-MM-DD') → Date` (UTC instant of 00:00 São Paulo, offset via Intl `longOffset`).
- `renewalWindow({ now, currentAccessUntil, durationDays })`: `start = max(now, currentAccessUntil ?? now)`; `endsAt = spMidnight(addDays(spDate(start), durationDays))`. Example: now 2026-10-19 15:00 BRT, 30 days → endsAt 2026-11-18 00:00 BRT (válida até 17/11/2026, 30 calendar days counting today). Renewing on 2026-11-10 while active until 2026-11-18 00:00 → start 2026-11-18 00:00, endsAt 2026-12-18 00:00.
- `isPeriodActive(p, now) = p.status !== 'encerrada' && p.startsAt <= now && now < p.endsAt`.
- `accessUntilOf(periods)` = max `endsAt` among non-ended periods (or null).
- `validUntilLabel(endsAt)` = pt-BR date of `endsAt − 1 ms` in São Paulo ("17 de novembro de 2026").
`access.ts` (server-only): `getAccessStatus(assinanteId, now = new Date())` → `{ state: 'ativa' | 'vencida' | 'encerrada' | 'sem-assinatura', validUntil?: string, startsAt?: string }` reading that subscriber's periods with `overrideAccess: true` (bounded, sorted by `-endsAt`). `requireActiveSubscription()` = `requireAssinante()` + status `ativa`, otherwise renders the inactive panel (no restricted markup in the HTML).
Hooks: subscriptions `afterChange`/`afterDelete` recompute `assinantes.accessUntil` (`context: { skipAudit: true }`).

### Pattern 6: Plans and "Assine Já" (ASS-05, D-02, D-03)
`plans` (labels "Plano"/"Planos", group "Assinantes"): `name` (text required), `durationDays` (number required, min 1, help "30 = mensal, 90 = trimestral, 180 = semestral, 365 = anual"), `price` (number required ≥ 0, "Preço (R$)"), `promoPrice` (number optional, must be < price, "Preço promocional (R$) — aparece como 'de R$ X por R$ Y'"), `paymentUrl` (text optional, must be `https://`; help "Link de pagamento do PagBank com o valor deste plano. Se o preço mudar, gere um link novo no PagBank."), `description` (textarea ≤ 140, optional), `active` (checkbox default true, "Mostrar na página Assine Já"), `order` (number). Access: read staff all / anonymous `{ active: { equals: true } }`; writes staff. Hooks `expire(['plans'])`.
Seed (data migration, only when the collection is empty): Mensal 30 d R$ 30; Trimestral 90 d R$ 75; Semestral 180 d R$ 135; Anual 365 d R$ 240; `paymentUrl` empty (old links carry old prices, D-02). The page shows "Pagar" only when a link exists; otherwise "Combinar pelo WhatsApp".
`/assine-ja` (dynamic, data from `cached` with tag `plans` + contact global): H1 "Assine Já", plan cards (name, "30 dias", price or "de R$ 75 por R$ 60"), "Pagar" (external, `rel="noopener noreferrer"`), steps "Como assinar": 1 pague pelo link, 2 envie o comprovante pelo WhatsApp com nome e e-mail, 3 a equipe cria o acesso e envia a senha provisória pelo WhatsApp; "Enviar comprovante pelo WhatsApp" (`wa.me/{contact.whatsapp}?text=…`); "Já é assinante? Entrar". Old WordPress path `/assine-ja/` is preserved (MIG-03 friendly). Listed in sitemap and nav.

### Pattern 7: Passwords without e-mail (D-04; ASS-02 substitute)
- **Temporary password by staff:** native create/edit form; `beforeOperation` sees `data.password` → sets `mustChangePassword: true` when the actor is staff and records `req.context.passwordSetBy = 'equipe'` for the audit hook. Password update in Payload clears all other sessions (`update.js`: sessions filtered to the current sid only when the actor is the same user) → the subscriber is logged out everywhere.
- **Reset link by staff:** service `createPasswordLink(payload, { assinanteId, staff })` → `payload.forgotPassword({ collection: 'assinantes', data: { email }, disableEmail: true, context: { staffPasswordLink: true } })` returns the token → URL `${NEXT_PUBLIC_SERVER_URL}/nova-senha?token=…` (48 h, single use). Shown once in the panel with "Copiar" and "Enviar pelo WhatsApp" (wa.me to the subscriber's `whatsapp`). The token is never written to the audit log.
- **`/nova-senha`** (public, noindex): form new password + confirm (min 8) → `payload.resetPassword({ collection: 'assinantes', data: { token, password }, overrideAccess: true })` (returns a token; sets the cookie like login) → clears `mustChangePassword` (context `skipAudit`) + audit "senha trocada pelo assinante (link)" → redirect to `/area-do-assinante`. Invalid/expired token → "Este link expirou ou já foi usado. Peça um novo para a equipe pelo WhatsApp."
- **Self change** (`/area-do-assinante/senha`): current + new + confirm; verify current with `payload.login` (counts toward lockout — intended); `payload.update({ collection: 'assinantes', id, data: { password }, overrideAccess: true, user })` passing the authenticated user (keeps the current session `sid`, revokes others); clears `mustChangePassword`; audit actor type `assinante`.
- Banner on every members page while `mustChangePassword`: "Você está usando uma senha provisória. Troque agora."

### Pattern 8: Staff actions in the panel (PAINEL-05, D-05, D-06)
Service (`service.ts`, int-tested without UI):
- `grantOrRenew(payload, { assinanteId, planId | null, durationDays?, amount, method, paidAt, note, staffUser, now })`: reads current `accessUntil` from active periods; window via `renewalWindow`; creates a `subscriptions` doc with `context: { auditAction: currentActive ? 'acesso-renovado' : 'acesso-liberado' }`; returns `{ startsAt, endsAt, validUntilLabel }`. `amount` defaults to `promoPrice ?? price` of the plan. Without a plan (cortesia) `durationDays` is required.
- `endAccess(payload, { assinanteId, reason, staffUser, now })`: every period with `status: 'ativa'` and `endsAt > now` → `status: 'encerrada'`, `closedAt: now`; one audit entry `acesso-encerrado` with the reason; returns count.
Endpoints on `assinantes` (`endpoints` in the collection config): `GET /:id/situacao` (status, accessUntil, active plans, last 10 periods), `POST /:id/liberar`, `POST /:id/encerrar`, `POST /:id/link-senha` (slice 5). Each handler: `if (!isStaff({ req })) return Response.json({ message: 'Sem permissão' }, { status: 403 })`, parse `await req.json?.()`, validate, call the service, return JSON. Path param via `req.routeParams?.id` (verify in 3.91).
Admin UI: `type: 'ui'` field `assinaturaPainel` with `admin.components.Field: '/components/admin/assinantes/AssinaturaPanel#AssinaturaPanel'` (client component, `useDocumentInfo()` for the id; hidden on create). Shows "Situação: Ativa — válida até 17/11/2026" / "Vencida em …" / "Sem assinatura"; form Plano (active plans + "Cortesia / outro prazo" with days input), Valor (prefilled), Forma de pagamento, Data do pagamento (today), Observação; button "Liberar acesso" or "Renovar" with the preview "Acesso até {data}" computed with the same pure `renewalWindow`; "Encerrar acesso agora" with a reason prompt and `confirm()`; after success `router.refresh()`. Joins on the subscriber show "Períodos" and "Histórico" read-only.

### Pattern 9: Expiring in 7 days (PAINEL-06)
`getExpiringSoon(payload, now, days = 7)` → subscribers with `accessUntil > now` and `<= now + days` (sorted ascending, limit 100). Rendered by a `beforeDashboard` server component "Vencem nos próximos 7 dias" (name, "vence em 17/11 (3 dias)", WhatsApp button with pre-filled text "Olá, {nome}! Sua assinatura do Paraíso vence em {data}. Quer renovar?", link "Abrir" to the subscriber) and a link "Ver todos os assinantes por vencimento" to the list sorted by `accessUntil`. Empty: "Nenhuma assinatura vence nos próximos 7 dias."
Note: `accessUntil` is the latest non-ended period end; a subscriber who already renewed does not appear.

### Pattern 10: Append-only audit log (PAINEL-08, D-06)
`audit-log` (labels "Registro"/"Registro de ações", group "Assinantes", `useAsTitle: 'summary'`, defaultColumns `['createdAt','actorLabel','action','assinanteLabel','summary']`, default sort `-createdAt`): `action` select (`conta-criada`, `conta-editada`, `conta-excluida`, `acesso-liberado`, `acesso-renovado`, `acesso-encerrado`, `periodo-corrigido`, `senha-definida-pela-equipe`, `link-de-senha-gerado`, `senha-trocada-pelo-assinante`), `actorType` (`equipe` | `assinante` | `sistema`), `actor` (rel users), `actorLabel` (text snapshot), `assinante` (rel, optional), `assinanteLabel` (text snapshot "Nome <e-mail>"), `summary` (text, pt sentence), `details` (json: changed fields before/after; payment {plano, valor, forma, data, observação}). Access: read staff; create/update/delete **false** (UI shows no "Criar novo", no edit, no delete); writes only via `writeAudit(payload, entry, req)` with `overrideAccess: true` and the same `req` (same transaction). `diffForAudit(before, after)` drops `password`, `hash`, `salt`, `sessions`, `resetPasswordToken`, `resetPasswordExpiration`, `loginAttempts`, `lockUntil`, `updatedAt` (unit-tested). Hooks: assinantes afterChange (create/update) and afterDelete; subscriptions afterChange (create uses `context.auditAction`; update → `acesso-encerrado` when status flips, else `periodo-corrigido`); skipped when `req.context.skipAudit`.

### Phase 6 compatibility (design now, implement later)
- Login always goes through our `entrar` action (not the REST `/api/assinantes/login` from a client form). Phase 6 adds, inside that action, a fallback when `payload.login` throws `AuthenticationError`: load the subscriber by e-mail (overrideAccess), and if it has `legacyPasswordHash` verify it — `$wp$2y$…`: bcrypt over `base64(HMAC-SHA384(key 'wp-sha384', trim(password)))` (WordPress 6.8+); `$P$…`: phpass portable — then `payload.update({ password })` (writes PBKDF2 hash/salt), clear the legacy field, retry `payload.login`.
- Phase 6 adds `legacyPasswordHash` (field `access.read: () => false`, hidden) and `wpUserId` (unique) in its own migration; imports create subscribers with `context: { trustedCreate: true }`, a random password and `mustChangePassword: false`, and one `subscriptions` period per active WP user (`_expire_user_date` → `endsAt`, method `outro`, note "Migrado do WordPress").
- E-mail is the login identifier (WordPress users all have `user_email`; unique in WP).

### Anti-Patterns to Avoid
- `Boolean(req.user)` as "staff" (Pattern 2).
- An `active`/`expired` boolean flipped by a job (drifts, needs cron).
- Auth checks only in the members layout (not re-run on navigation; does not gate actions).
- Caching anything subscriber-specific with `cached()`; adding members pages to the sitemap.
- Storing payment receipts (images with bank data) — keep a text note only (LGPD minimisation).
- Logging tokens or passwords (audit `details`, console).
- Letting the client choose dates for "renovar" in the browser clock: the server recomputes with `new Date()`; the UI preview is advisory only.
- Hand-rolled JWT/cookies when Payload already signs and verifies them.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead |
|---------|-------------|-------------|
| Password hashing, lockout, sessions | custom tables/JWT | Payload auth collection (`useSessions`, `maxLoginAttempts`) |
| Reset tokens | random tokens in a custom field | `payload.forgotPassword({ disableEmail: true })` + `payload.resetPassword` |
| Session revocation on password change | manual session wipe | Payload update op (keeps only the current `sid`) |
| Admin list/filters | custom list page | Payload list view + `defaultColumns` + sort by `accessUntil` |
| Date-only TZ math | string slicing of ISO | `Intl.DateTimeFormat` with `timeZone` |

## Common Pitfalls

### Pitfall 1: Shared auth cookie
Staff and subscribers share `payload-token`. Logging in on `/entrar` in the same browser replaces the admin session. Guide: test subscriber logins in a private window. e2e: separate `browser.newContext()` per role.

### Pitfall 2: `first-register` and `forgot-password` REST endpoints
Exist for every auth collection. `first-register` bypasses access when the collection is empty (production state until Phase 6). Guard both in `beforeOperation` and test with REST calls (expect 403).

### Pitfall 3: Parallel migrations
Each `migrate:create` snapshots the whole schema. Slices that change schema run in separate sequential waves; tests share the single `paraiso_test` database, so plans never run in parallel.

### Pitfall 4: Timezone off-by-one
Containers run UTC; staff and subscribers think in Brasília dates. All comparisons use instants; all labels use São Paulo; `endsAt` is exclusive. Unit tests cover 23:30 BRT (02:30 UTC next day) and the exact `endsAt` instant.

### Pitfall 5: Layout-only guard
See Pattern 3. Every page calls the DAL; every server action re-checks the principal.

### Pitfall 6: Audit gaps
Hooks run for Local API and REST; `payload.db.*` writes (Payload's own session/login-attempt bookkeeping, `resetPassword`) bypass hooks → the `/nova-senha` action writes its audit entry explicitly. Hook recursion (accessUntil update re-triggering audit) prevented with `context.skipAudit`.

### Pitfall 7: Field-level read access returns undefined in admin
`staffNotes`/`mustChangePassword` restricted fields must still be readable by staff in the admin (field access receives `req.user` staff → true).

### Pitfall 8: Payment link edits after price change
The PagBank link fixes the amount; changing `price` without a new link charges the old value. Help text on `price` and `paymentUrl` says so; the staff guide repeats it.

### Known Threat Patterns
| Pattern | STRIDE | Mitigation |
|---------|--------|------------|
| Subscriber uses staff APIs | E | `isStaff` by collection; regression test |
| Public account creation via first-register | S/E | `beforeOperation` guard; REST test |
| Brute force / credential stuffing | S | lockout; generic message |
| Open redirect via `?next=` | T | `safeNext` allowlist |
